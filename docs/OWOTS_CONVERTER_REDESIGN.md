# 鬼武者服装转换器 V2 设计稿

日期：2026-09-18。状态：**已进入开发，以下保留原设计决策；实际界面已简化为原生程序**。[早期复杂原型](OWOTS_CONVERTER_PROTOTYPE.html)不再作为界面验收标准。

2026-09-18 开发修订：普通用户窗口仅显示游戏目录、输出目录、拖入区和结果，只有问题发生时显示原因。常规多部位、多外观、纯纹理、占位隐藏与分别注册的声明穿戴已经进入实现。按用户确认的既有成功经验，未被部位直接引用且仅旋转不匹配的 93 关节独立骨架自动回退到 BODY mesh 内嵌休止数据；不迁移该骨架的旋转或绑定位置，结果提示需要测试。OniSwordModXiaoShen 已离线转换为 4 个包含 BODY/HEAD/HAIR 的条目。扩展拓扑和脚本功能仍不强行兼容。`rules.equip` 已通过核心回归与运行时打包编译，尚未据此宣称游戏内视觉验收。

当前实现位于 `mod-converter/batch_converter.py`、`converter_gui.py`。PFB/普通 USER 使用等长路径片段改写，逐字节证明片段外数据不变；catalog 行选择继续使用严格结构化读写器。已生成常规真实样本结果，测试资产与详细记录留在工作区 `_validation/converter-development-20260918/`。下方规划中的人工挑选流程、等级文案和全面语义等价合并不是全部已实现功能。

本文依据本仓库现行代码、原生资源索引、仓库经验以及本机测试包的资产结构。测试包的说明文档、描述、INI 内容与脚本内容均未作为分析依据。包名只用于标识样本。

## 1. 产品决定

用户打开程序，把文件夹、ZIP、RAR、7z 或普通 KPKA PAK 拖进窗口；程序立即分析，自动列出将生成的服装和武器。映射唯一、输出可校验的条目自动进入转换，结果直接留在列表中。需要选择的条目停在本行，其他独立条目继续。

核心模型改为 **输入包 → 资源覆盖图 → 外观方案 → 部位计划与穿戴声明 → 独立服装包**。BODY/HEAD/HAIR 合并为身体条目；可见披风、护手分别注册独立条目，由身体的“声明穿戴”规则关联。玩家穿戴身体时自动带上配套附件，随后可直接换成其他披风或护手。

转换器只负责路径隔离、配置生成和附属资产引用。它不判断源 Mod 在游戏里是否能正常工作，不修模、不修骨骼、不重新绑定、不改变作者的材质和动画意图。需要验证的是“能否完整表达和正确写出这次迁移”。读取失败不等于源 Mod 有问题。

默认输出到程序可写位置下的 `Converted Mods/<批次>/`，不可写时请求选择一个位置并记住。源文件和游戏始终只读；“移动路径”在实现上是复制到新命名空间并重写引用。首次自动发现游戏路径，找不到时仍做资产盘点，只有依赖原版资源的条目提示“选择游戏目录”。

### 状态文案

不把“游戏能运行”混进转换等级，也不用无依据的成功百分比。

| 显示状态 | 严格含义 | 默认行为 |
| --- | --- | --- |
| **完整转换** | 发布后，部位归属明确；范围内资源全部有去向；必要引用和写回校验通过；没有已知语义降级 | 自动导出；可打开结果 |
| **需要测试** | 能生成结构完整的外观包，但存在未验证的表现差异，例如保留未识别占位网格、隐藏语义替代、HQ 使用路径未验证 | 自动导出，逐项显示测试点 |
| **可能失败** | 能生成静态外观，但已知有行为可能不能表达，或存在未经验证的必要外部依赖 | 不自动导出；本行提供“仍生成静态外观”并说明具体损失 |
| **需要选择** | 资源读得出来，但有不能由证据唯一解决的组合/变体归属 | 给出可比较的候选；选择后自动继续 |
| **无法转换** | 必要配置无法可靠解析或重写、必须复制的文件无法读取、无法确定必要资源路径，或目标运行时不能表达该方案 | 不输出安装包；展示具体文件、原因和可行下一步 |

“完整转换”对应用户所说的“完美转换”，建议使用前者以免误解为已验证游戏表现。如果产品坚持使用“完美转换”，必须常显“配置与路径完整，游戏表现未验证”。分析阶段用“预计完整转换”，只有发布校验通过后才去掉“预计”。

**处理进度、转换等级、实机验证是三个独立字段**：例如“已导出 · 需要测试 · 游戏表现未验证”。用户后来标记“本机测试通过”也不能改写结构证据，更不能替所有游戏版本背书。

### 已确认的实现缺口

| 当前代码 | 限制 | 设计调整 |
| --- | --- | --- |
| `ConverterWindow`、`InputBundle.load` | 手动输入/检查/转换；CLI 核心仅文件夹和 PAK；不是拖入即批量分析的工作流 | 新增输入队列和容器展开层，GUI 只展示计划和事件 |

## 3. 窗口与交互

### 默认界面

上方：产品名、游戏版本/索引状态、“转换后保存到…”。不要求玩家先填写 ID、Catalog、PFB 或部位名。

空白时：大拖放区，“把 Mod 拖到这里”，以及“选择文件”“选择文件夹”两个等效入口。支持多次追加、多个文件一起拖入。常显“自动分析并转换明确的外观；需要选择的项目会单独停下”。

有任务时：左侧为输入包与生成条目树；右侧为选中条目详情；底部显示真实数量，例如“输入 3 个包 · 识别 2 套身体、1 件披风、1 件护手、2 件武器 · 已导出 5 项 · 1 项需要选择”。额外显示“身体 A 会同时穿戴披风 C、护手 G”。状态统计以**注册条目**为单位，原生目标数、候选数、资源数单独标示；一套关联外观的体验数量与其内部注册数量分开。

### 详情的阅读顺序

1. **会得到什么**：外观名称、分类、包含部位、对应原生目标、输出条目数。
2. **转换程度**：状态文字，最多三个主要原因；点击展开其余原因。
3. **部位去向表**：部位 / 处理方式 / 依据 / 输出或原版引用。
4. **未转换内容**：准确区分“说明文件”“范围外资源”“未识别资源”“属于其他条目的资源”。
5. **高级证据**：完整路径、native ID、PFB 引用链、读写器错误码、哈希、计划版本。可以复制诊断。

部位处理方式包括：`使用 Mod 资产`、`引用指定原版资产`、`声明隐藏`、`保留原占位模型`、`未涉及（沿用原生）`；身体详情另设“随服装穿戴”，列出独立披风/护手条目及关联声明。其中“引用指定原版”和“未涉及”必须区分；前者固定到被替换方案的原版目标，后者遵循系统现有原生回退。

### 需要选择时

以可读名称、受影响部位和具体差异并排列出候选。例如“覆盖原服装 A”和“覆盖原服装 B”；显示是材质不同、物理不同、隐藏不同还是只是原生适配目标不同。不把 normal/HQ 原样当作两套服装让用户猜。高级入口才显示路径和 ID。

解析证明是不同外观时默认分别输出；证明是同一方案不同原生目标时才合并显示。证据不足时保留候选，不做所有 BODY × HEAD × HAIR 的笛卡尔组合。用户可以选一个或“按这两个候选分别生成”，选择被记录为用户决定。

### 进度与失败

队列阶段：发现输入 → 解包/索引 → 建立引用 → 整理外观 → 写出 → 校验 → 完成。显示当前阶段与已处理文件/总文件/字节，不用虚构百分比。分析缓存命中也显示依据的游戏版本。

支持取消当前任务、取消未开始任务、失败后只重试受影响条目。一个条目失败不取消其他可独立导出的条目；共享依赖故障必须传播到所有受影响条目。暂停等待选择时不占用转换执行槽。

完成页逐项列出已导出的服装和武器、包含部位、声明隐藏、原版引用、未带出的文件及原因；提供“打开输出文件夹”“查看转换报告”“重新分析”。不得只显示一个“成功”。

界面使用系统中文字体、清晰的行式列表与状态标签；状态有文字和符号，不单靠颜色。主操作可键盘访问，拖放有按钮替代，错误摘要可定位具体条目；后台事件不得抢走焦点。保留现有中英文自动选择机制，路径/ID/错误码不翻译。

## 4. OWOTS 资产模型

输入包不是外观单位，文件夹名也不是关联证据。使用下列对象：

| 对象 | 用途 |
| --- | --- |
| InputPackage / SourceLayer | 拖入的原始容器及内部资源根；记录来源，避免把不同选装子目录提前叠加 |
| AssetKey | 规范化逻辑路径、数值格式版本、base/streaming 通道；保留原始路径供诊断 |
| NativePartTarget | 来自真实 Catalog 行的部位、native ID、PFB、角色/形态/质量分支 |
| AppearancePlan | 一个注册条目的部位方案、目标、隐藏/穿戴声明与原版回退，带证据和未决选择 |
| ResourceDisposition | 每个输入资产最终由哪些条目使用，或以什么理由省略/阻塞 |
| CapabilityProfile | 目标游戏/运行时的可表达能力与读写器支持范围，不代表源 Mod 能正常运行 |

依赖图示例：

```text
原生 Catalog 的准确行
    └─ 部位 PFB ─┬─ mesh
                 ├─ MDF ── TEX（base + streaming）
                 └─ USER / chain2 / 其他实际被引用的附属资产

选择的 SourceLayer 按准确路径覆盖上述原版图
    └─ 变化资产 + 为重定向所需的祖先配置 → 私有路径
       未变化且无需重定向的依赖 → 保持原版路径
```

数值格式版本沿用仓库已验证的版本表，并按读写器能力确认；不靠重命名后缀“转换格式”。对于不需要解析和改写的叶子资产，只要可读取和完整复制，允许保持原字节并给出“格式/内容未验证”提示；不要以可选几何探测失败阻断一个已闭合的静态迁移。必须改写的结构不认识时才阻断该条目。

本机原版参考必须来自游戏正式 PAK/补丁/DLC，不能读取游戏根目录中已安装 Mod 的松散覆盖作为“原版”。记录补丁优先级、路径索引版本、Catalog/PFB 哈希；缓存按这些值失效。缺少 DLC 时标明哪条引用需要 DLC，不能偷偷换成另一个身体。

## 5. 分组与多外观识别

1. **发现资源根**。忽略任意层包装目录；识别独立的 `natives/stm`、PAK 和资源结构。ZIP/RAR/7z 使用可信解包适配器在隔离目录展开，处理中文/空格路径。只读目录表识别安全路径、大小上限与层级，不执行包内程序；内嵌机器路径清单可作路径候选，但必须核对哈希与覆盖范围，不读取说明文字推断功能。
2. **建立来源层**。多个根覆盖同一 AssetKey 且字节不同，先标记互斥分支；同一路径相同字节可合并来源。包装名、README 中的安装步骤不能作为层叠优先级；无法判定的选装顺序必须让用户选择。
3. **定位原生目标**。Mod 自带 PFB/Catalog 的结构化引用优先；其余通过版本化的反向索引找原生部位，再用原版实际图验证。文件名相似只用于缩小搜索范围。
4. **创建一致的方案**。同角色/形态及同一覆盖分支的 BODY+HEAD+HAIR 等归为身体条目；配套可见 CLOAK/GAUNTLET 分别注册，并由身体声明穿戴。不确定是否配套时不强行关联。武器以其原生武器根及鞘/附属图分组，不按包名中的 sword 推测，不按公共材质把整包连成一个外观。
5. **区分目标与外观**。若覆盖内容、依赖映射、可见性、骨架声明、物理设置及有效 PFB 结构均等价，可以归为一个外观、多个来源目标。只比较 BODY mesh 哈希不够。任一必要语义不同则保留为不同方案或待选择项。
6. **normal/HQ/AC/形态分支**。HQ 不自动计为第二套服装，也不能直接丢弃。验证它们的引用差异和运行时实际加载方式；同一质量族以共同外观分组，资源均登记去向。若当前运行时不能表达源包的不同分支，则“需要测试/可能失败/需要选择”，准确说明哪条路径不能等价复现。当前插件的菜单角色同步不能当作已支持所有 HQ 分支的证明。
7. **检查资源覆盖账本**。新方案归属成功后，其他方案使用的输入不再作为本方案未消费错误。无已知使用者的外观资产继续显示“未识别归属”，不能伪装成无关文件。

如果同一套外观的多个来源目标等价，最终仍需选定可验证的 PFB 模板并记录全部支持目标；不要把多个 BODY PFB 填进同一个槽位。只有不依赖目标差异的私有方案才可直接去重成一个运行时条目。

## 6. 空模、小模型与隐藏意图

隐藏识别是可选的语义优化，不能成为正常搬运的前置条件。避免“文件小于 N KB 就隐藏”或“面数低于 N 就删除”。

| 证据结论 | 处理 | 等级影响 |
| --- | --- | --- |
| 已可靠解析；所有被使用的 LOD/分支均无可绘制面，且没有其他可见子对象；部位可由运行时表达隐藏 | 该部位不再发布占位 PFB，转为 `rules.hideParts` | 至少需要测试，验证隐藏替代的实际表现 |
| 极少有效面/极小模型，并有强证据（顶点空间、相对原版尺度、实际 PFB 可见分支及依赖均支持占位判断） | 达到已验证规则时自动声明隐藏，保留证据及“改为保留原模型”入口 | 需要测试 |
| 只有少面数/文件大小线索、探测失败、影子/布料/其他子对象未确认 | 保留原 mesh、PFB 及必要依赖，正确加入整套服装 | 需要测试；说明未自动隐藏 |
| 模型中部分网格删小，仍有可见部分 | 整个模型保留，不把局部删除扩大为整个部位隐藏 | 按其他风险判定 |
| 游戏未提供对应衣橱部位，或隐藏运行时不支持该对象 | 保留原资源及可表达引用；若它只由范围外行为控制则说明损失 | 需要测试/可能失败，必要迁移无法表达时阻塞 |

几何探测读取有效索引引用的顶点和变换后的空间大小，检查有限数值、退化面、各 LOD、shadow/occlusion 分支和 PFB 内子对象；不信任可能过时的头部包围盒。Skin mesh 骨骼数与 actor 的 93 关节契约是不同概念，不能拿两者相等作为判据。

先用 `有效面≤32`、`几何尺度≤同目标原版的1%` 之类阈值进行**候选召回**，不是默认自动隐藏规则。阈值须用真实占位和正常的小饰品对照标定。透明平面、很小的金属饰品、低 LOD 和移到远处的模型均可能误判；证据冲突时回退保留。

转为隐藏时，`parts[]` 与 `hideParts` 不得同时出现同一个部位。删除的是输出图中不再需要的占位根；共享 MDF/TEX/chain 仍被别处引用时必须保留。不同部位分别判定，不能因为 BODY 是一体模型就默认隐藏所有其他部位。

原生 BODY 的 `IsInvisibleHead`/`IsVisibleCloak`、`FixHairID`/`FixGauntletID` 是额外基线证据。只有对应目标一致时使用；Mod 明确提供可见部位时，不能被原生默认隐藏规则静默覆盖。强制原生护手不等于存在“隐藏护手”标志。

## 7. 纯纹理与局部覆盖

纯纹理的识别链：`TEX → 哪些原版 MDF 引用它 → 哪些 PFB 使用该 MDF → Catalog 原生部位/外观`。需要补充版本化反向依赖索引；现有 `owots_native_parts.json` 仅有部位/PFB/Catalog 记录，不能独自完成这一步。索引可从本机按需建立并缓存，发布索引只含路径、关系和版本证据，不含游戏资产。

示例：源包仅提供身体底色 TEX：

```text
私有 Catalog → 私有 BODY PFB
                   ├─ 原版 BODY mesh（保持原路径）
                   ├─ 私有 MDF（只改纹理引用）
                   │     ├─ 私有底色 TEX
                   │     └─ 原版法线/其他未修改纹理
                   └─ 未变化的其他原版依赖
```

原版 PFB/MDF 若包含指向私有变化资源的引用，就必须复制并改写；“未修改的用原版”不等于让原版 MDF 继续指向原版底色。原版完整资源不打进通用程序发行包，用户本机生成必要私有配置。

仅 HEAD 或 HAIR 被替换时允许 body 分类只有这一部位。源包未涉及身体就维持原生身体；当某个**被转换部位内部**只改了纹理/模型的一部分，其他内容必须沿用该目标的准确原版资源。子网格级的模型编辑按原文件完整复制，不在转换阶段重新拼顶点。

共享 TEX 对应多套服装时，先列出所有受影响的衣橱目标；不能随便挑第一套，不能改成全局共享纹理覆盖。明确属于不同外观的目标分别生成条目；等价目标按第5节归并；玩家不需要的目标可以取消选中。

base/streaming 必须作为一个逻辑纹理的伴随通道处理。完整配对就保留；仅 base 或仅 streaming 改动时，按格式和该游戏的实际伴随关系验证能否补原版另一半，不能盲目混配。无法确认时明确说明缺哪一半、是否会回退分辨率，并降级或阻塞必要引用。沿用 `texture_resolution.py` 的保守提升能力，禁止因为基础文件能读取就宣称高清已经正确。

## 8. 分别注册，通过规则声明穿戴

按用户补充确定：保持现有四分类，每个条目只提供本分类部位。BODY+HEAD+HAIR 放在身体 manifest 的多个 `parts[]` 中；配套披风、护手各有自己的 manifest、ID、Catalog/PFB，可单独出现在衣橱中。身体新增 `rules.equip` 声明，指定穿戴身体时带上的附件。

以下是**新增规则草案**，尚不能直接交给现有运行时。字段名在实现时与现有 manifest 模型统一：

```json
{
  "id": "author.outfit_a.body",
  "category": "body",
  "parts": [
    { "part": "BODY", "catalog": "mods/.../body.user", "prefab": "mods/.../body.pfb" },
    { "part": "HEAD", "catalog": "mods/.../head.user", "prefab": "mods/.../head.pfb" },
    { "part": "HAIR", "catalog": "mods/.../hair.user", "prefab": "mods/.../hair.pfb" }
  ],
  "rules": {
    "equip": {
      "cloak": "author.outfit_a.cloak",
      "gauntlet": "author.outfit_a.gauntlet"
    },
    "hideParts": []
  }
}
```

上例省略了完整 manifest 所需的版本和展示字段；`...` 为设计占位，不是可安装配置。配套两个子条目分别为 `category: cloak`、`category: gauntlet`，它们的 ID 必须与声明严格对应。`rules.equip` 的值引用真实注册 ID，绝不引用 `runtime.wardrobe.*` 临时组合 ID。

### 用户动作与优先级

| 用户动作 | 身体 | 披风 | 护手 |
| --- | --- | --- | --- |
| 初始状态 | 原生 | 用户原选择 C0 | 用户原选择 G0 |
| 穿戴服装 A | A.body | 声明带上 A.cloak | 声明带上 A.gauntlet |
| 再穿戴其他护手 G1 | A.body 保持 | A.cloak 保持 | **立即切到 G1，手动选择优先** |
| 取消服装 A | 原生 | 撤销 A 的声明，恢复 C0 | 保留用户后来选的 G1 |
| 改穿服装 B | B.body | B 有声明则带上，否则恢复基础选择 | B 有声明则带上，否则保留基础选择 |
| 用户明确重新穿戴 A | A.body，产生一次新的穿戴动作 | 重新按 A 声明穿戴 | 重新按 A 声明穿戴 |

**一次身体穿戴动作建立默认配套；后续手动动作覆盖对应类别。** 用户再次点击其他护手直接生效，无需先取消身体，也不因声明穿戴本身增加确认弹窗。UI 标签区分“由服装 A 声明穿戴”和“用户已覆盖配套”。声明不能每帧重新写入选择把用户换回去。显式重新穿戴身体可恢复整套默认；菜单重建、轮询和读档都不算新的用户穿戴动作。

每个类别保留 `基础用户选择`、`当前身体的声明选择`、`本次穿戴之后的用户覆盖` 三项状态。当前动作标识绑定声明来源，避免上套服装的临时覆盖污染下一套；基础用户选择保留以供撤销恢复。用户在穿戴期间选了 G1，就更新基础选择和本次覆盖；取消身体不会把已经明确选过的 G1 换回 G0。用户明确关闭配件显示时，沿用现有显示开关最高优先级。

### 与隐藏/冲突规则共用

- 成功识别的删除模型转换为身体的 `hideParts`；可见配套转换为 `equip`。无法识别的披风/护手占位仍单独注册原模型，由身体声明穿戴，保留作者隐藏意图。
- 同一来源不能一边声明穿戴披风、一边隐藏 CLOAK 或声明与 cloak 不兼容；生成计划时报告规则矛盾。子条目的隐藏/冲突继续进入现有组合规则，但不能隐藏自己的提供部位。
- 声明穿戴先决定各分类的候选选择，再交给现有隐藏/互斥/显示开关与来源授权求解；只有实际生效条目施加规则。被用户覆盖的配套条目不再继续施加旧规则。
- 用户手动穿戴其他护手覆盖 `equip.gauntlet` 即可；若另有独立的隐藏/互斥声明仍生效，复用现有按类别、按来源的强制穿戴规则，不新增第二套冲突系统，也不能通过 `equip` 绕过它。
- 首版只开放 body → cloak/gauntlet，引用类别必须匹配，禁止自引用、循环或多级递归声明。武器仍是独立选择；不因为同包就自动换武器。

### 运行时事务与恢复

一次穿戴身体，把 body 与声明附件放进同一个现有组合求解/预加载/切换事务。先确认所有目标 ID、PFB 及能力可用；必要附件缺失或加载失败时，保持原组合并明确说明缺哪件，不能只换身体后留下半套却报成功。单独手动换护手只改变护手的用户选择来源，继续复用现有组合切换和资源生命周期。

取消身体仅撤销它拥有的声明，不全局清空披风/护手。切换身体先撤销旧来源，再在同一事务中应用新来源。存档记录基础选择、声明来源以及仍适用的用户覆盖；读档重建同样的结果，不能以“再次穿戴”把已手选的 G1 改回 A.gauntlet。世界角色与菜单角色使用同一求解结果。

### 协议与旧版本

保持 `category`、`parts[]` 的现有约束；新增的是 `rules.equip` 语义和上述来源状态。普通无声明穿戴条目继续使用 schema 2。为避免旧运行时悄悄忽略新规则，**暂定含 `rules.equip` 的父条目升级为 schema 3**，旧读取器按未知版本拒绝；子条目仍可使用 schema 2。这里的版本变化只负责识别新规则，不放宽身体的部位分类。

转换器读取目标运行时能力 `declared-equip-v1`（拟定），再决定是否能生成并验证父条目。旧版目标可明确导出三个独立条目并标注“本版需手动分别穿戴”；不能冒充已实现自动带上附件。正式发布必须验证旧版拒绝路径和新版规则读回。

## 9. 范围外内容和骨架

范围按资源角色和实际引用判定，不能只看扩展名：

| 输入 | 处理 |
| --- | --- |
| mesh、MDF、TEX、模型需要的 PFB/USER、chain2 等 | 建立图、保留、按需要重写；保持作者原始内容 |
| 原生 Catalog | 只提取验证过的目标行到私有 Catalog，不复制整个全局替换表 |
| 同拓扑 actor 骨架声明 | 沿用已经存在的窄范围能力；只为准确绑定到 BODY 的资源生成声明，不做修复/重定向 |
| 扩展 actor、额外动作或脚本组件绑定 | 静态迁移可能缺少行为；仅能完整独立保留的静态部分可继续，并清楚列出损失 |
| Lua/DLL/ASI/可执行内容、全局玩法 USER、UI/音频等 | 不执行、不带进静态服装包；若包含已知/不能排除的外观依赖，标为可能失败 |
| 文本说明、INI 展示描述、预览图 | 不参与识别。本轮不读取内容；无需因此把可用外观判为可能失败 |
| 归属未知的 mesh/TEX 等外观资源 | 显示“未识别的外观资源”，继续尝试分组；不能当作无关文件静默忽略 |

源 Mod 的 mesh 无法做可选几何探测时，仍可原样迁移并保留作者占位意图。无法表达的 actor 扩展不被转换器修复；准确显示“这些额外绑定/行为未被迁移”，不要泛称“骨骼不合格”。

私有 `/90` fbxskel 永远不写到游戏全局 `/90` 原路径。同拓扑声明或 BODY mesh rest 方式以现有实现为准；一份 rig 对应哪个身体不明时不选第一份，也不自动去掉显式 rig 改用另一种体型来源。可以把未激活的原 rig 保留在私有资产区并记录它没有运行时作用。

范围外行为可以警告后生成静态外观；**必要结构不能可靠重写、路径不能确定**时，不能靠“用户接受风险”生成虚假的安装成功。这是迁移能力限制，不是判断源 Mod 好坏。

## 10. 原因系统

每个原因包含：`code`、`scope`（包/条目/部位/资源）、`conversionImpact`、中文/英文标题、证据、处理结果、用户动作、受影响条目 ID。严重度是 UI 表现；不能直接把日志 warning 数量换算为风险分数。

| 新原因示例 | 玩家看到的内容 | 下一步 |
| --- | --- | --- |
| `TEXTURE_OWNER_UNRESOLVED` | “找到 5 张替换纹理，但还未找到引用它们的原版材质。” | 选择游戏目录/重建该版本索引 |
| `APPEARANCE_GROUP_AMBIGUOUS` | “两个身体方案共用这份头发，无法确认应该如何组合。” | 并排选择或分别生成 |
| `PLACEHOLDER_PRESERVED` | “头发模型很小，但无法可靠确认是占位；将保留作者模型。” | 无需处理，可看依据或手动声明隐藏 |
| `PLACEHOLDER_TO_HIDE` | “原头部占位已改为衣橱隐藏；不再复制它独占的空模资源。” | 测试世界/菜单/CG/恢复 |
| `OUT_OF_SCOPE_BEHAVIOR` | “包内有无法迁移的脚本/全局修改；静态外观可能缺少相关效果。” | 查看文件清单，仍生成静态外观 |
| `TEMPLATE_LAYOUT_UNSUPPORTED` | “转换器无法改写这个版本的 PFB。不是在判断你的模型是否能运行。” | 更新读写器/模板；不能只改后缀或勾选忽略 |
| `STREAMING_PAIR_UNVERIFIED` | “高清伴随纹理与基础纹理的配对未验证。” | 查看缺失通道、提供配套资源 |
| `RUNTIME_CAPABILITY_MISSING` | “目标衣橱不支持随身体自动穿戴配套护手。” | 更新衣橱或明确导出需手动分别穿戴的条目 |
| `UNMAPPED_APPEARANCE_ASSET` | “这个模型尚未分配到任何服装或武器。” | 查看候选；不得当作已全部转换 |

保留现有精确错误码用于诊断映射；RSZ 布局不匹配与 CRC 不匹配分开处理。CRC 实验输出不能是完整转换；原版模板版本不一致应优先修复索引/读写器，不让玩家靠大量技术选项碰运气。

汇总原则：必要迁移不可执行 → 无法转换；否则有未决用户选择 → 需要选择；否则有已知语义损失 → 可能失败；否则有具体未验证变化 → 需要测试；否则预计完整转换。包级 UI 同时展示各项数量；只要有未识别的范围内资产，就不能称“全包完整转换”。

## 11. 转换核心与界面的接口

保持 CLI 和 GUI 共用一个深模块，公开界面以四个操作为主：

```python
session = analyze(inputs, environment, policy, events)
plan = resolve(session, user_choices)
result = publish(plan, destination, events)
cancel(session_id)
```

`analyze` 生成可校验计划，不写安装包；GUI 在计划明确时自动调用 `publish`，所以技术上分两步、玩家仍然只需拖入。公开结果使用不可变、带版本的数据结构，GUI 不能自行猜 PFB、拼命令语义或解析自然语言日志决定状态。现有 CLI 参数可保留为兼容入口，但不能让新 GUI 围绕越来越多的开关工作。

内部职责：容器和资源根发现；游戏只读参考；正反向引用图；外观分组；占位证据；路径编译；写回校验与发布。真正存在差异的文件夹/ZIP/其他压缩包/PAK 可作为输入适配器，松散原版/游戏 PAK 可作为参考适配器；不为只有一种实现的每个步骤增加抽象框架。

每份 `AppearancePlan` 至少含：来源层、稳定方案 ID、分类、目标证据、部位根、逐部位处理方式、路径映射、隐藏/穿戴声明、依赖的注册条目 ID、原版外部引用、每个资产的处置、运行时能力要求、issues、未决 choices。**计划文件不是运行时 manifest**；探测数值、疑似原因、选择 UI 字段均放在转换报告中，不塞进 manifest。

计划绑定输入文件指纹、原版版本和模板指纹。发布前再次核对，源包变化则只重算受影响部分，不能继续使用过时的“预计完整”。稳定 ID 由持久的包/方案身份和用户选择构成，不靠列表序号；写到同一目标出现已有 ID 时提供新修订目录并告知共存/替换关系，不直接覆盖。

## 12. 输出、完整性与取消

默认一个输入包输出一个批次文件夹。存在声明穿戴的身体及其配套披风/护手放在同一个**关联安装包**，内部仍是三份独立注册 manifest；完成页显示“1 组关联外观 / 3 个注册条目”。单独武器或没有声明依赖的服装仍独立打包。原型勾选身体时自动勾选必要配套；不能取消配套输出却保留指向它的穿戴声明。

默认每个注册条目的私有资产各自带齐；内部缓存去重不改变安装关系。一个配件被多件身体声明穿戴时，报告明确列出共享注册依赖和受影响条目；首版同批关联包完整发布、不自动拆开卸载。已安装配件被删除时，运行时和下一次转换均报告缺失 ID，不让未解析声明悄悄失效。需要单独导出身体时，必须同时移除对应声明并说明行为变化。

```text
Converted Mods/<批次>/
  转换结果.html
  conversion-report.json
  服装_A_含配套附件/
    natives/stm/mods/<稳定ID>/...实际数值版本资源
    natives/stm/streaming/mods/<稳定ID>/...高清伴随资源
    reframework/data/owots_appearance_lab/mods/<稳定ID>.body/manifest.json
    reframework/data/owots_appearance_lab/mods/<稳定ID>.cloak/manifest.json
    reframework/data/owots_appearance_lab/mods/<稳定ID>.gauntlet/manifest.json
  武器_B/
    ...
```

每个独立包或关联包在同盘 staging 目录写出、读回、校验，再以新目录发布。检查每个 PFB/Catalog 行一致、私有路径无碰撞、资源闭包、外部原版引用可证明存在、base/streaming 去向、提供与隐藏不冲突、穿戴声明引用闭合、目标协议可读。关联身体和必要附件作为一个发布事务，不能先发布身体再让附件失败。输出覆盖账本满足“每个输入资源都有处置”；同一资源可被多条目消费，但在输入统计中只计一次。

取消只清理本次 staging，已经发布的独立条目保留并显示状态。失败条目只保留诊断，不留半成品伪装成成功包。不能自动安装到游戏，也不能发布到仓库或把测试资产带进转换器发行包。

## 13. 验收矩阵

| 场景 | 必须证明的结果 |
| --- | --- |
| 完整 BODY+HEAD+HAIR | 一个外观条目、三个正确的部位 PFB；无遗漏、无跨变体拼装 |
| 身体含配套 CLOAK/GAUNTLET | 分别注册三个条目；身体通过 rules.equip 带上附件；手选其他护手立即覆盖；取消身体保留用户后选护手 |
| 声明穿戴的读档/切换/缺失依赖 | 不重复强制默认附件；旧声明不污染新身体；缺件不留下半套；同批关联包一起发布 |
| 已确认隐藏占位 | 仅移除输出中的占位根，声明隐藏；共享依赖仍在；可回切保留方案 |
| 可疑或不可解析的小模型 | 原字节保留、PFB 正确引用；不误判成隐藏 |
| 一包多服装、多武器 | 每项独立方案和输出；服装数量、武器数量及名称与最终 manifest 对上 |
| 同一模型替换多个原生目标 | 有完整图等价证据才合并；否则分别生成或等待选择 |
| 部分网格/单部位替换 | Mod 资产正确指向；该部位未改资源来自准确原版；其他部位按基线策略处理 |
| 纯纹理 | 能通过 MDF 反查部位；私有 PFB/MDF 使用私有 TEX，mesh 等仍指向原版 |
| 共享纹理、多外观 | 不全局覆盖，不漏受影响目标；明确生成几项 |
| base-only / streaming-only / 配对 | 缺失通道有依据处理；不默默降到低清；完整文件保持最高可用分辨率 |
| normal/HQ/AC/多个包装根 | 不把质量分支计为服装，不混装互斥层，不丢输入文件 |
| 脚本/全局修改混包 | 不执行不携带行为；可生成部分静态外观，明确列出可能损失 |
| 必要模板、未知 hash、缺少 DLC | 原因可定位；不能因为用户勾选继续就伪造完整结果 |
| 单条失败、取消、重复拖入 | 其他独立条目继续；源文件未修改；无残留半包；重复文件提示复用/重新分析 |

真实样本作为端到端资产测试，断言计划/依赖/输出引用及处置完整性，不拿“进程退出0”当作验收。两份压缩包和目录的资产集合一致性需在容器支持实现后验证，不仅比较名称。

现有样本尚不能完整覆盖“多把独立武器”“多个确证不同服装”“正常小饰品不能被隐藏”“独立配件的声明穿戴与手动覆盖”等情形，需要添加受控的合成图/结构夹具或明确资产样本。原型中的演示数量不是这些样本已转换成功的结果。

实机测试只针对转换引入的行为：穿戴/撤销/切换，世界与菜单角色，已知 CG、读档，隐藏恢复、布料/护手、最高 mesh LOD 与纹理分辨率。源 Mod 本来存在的穿模或动画问题记录为外部现象，不交给转换器修复。骨架、资源解析和 operator 完成不能替代视觉验收。

## 14. 实施顺序

1. **先做计划核心和明确报告**：资源根修正、容器入口、资源处置账本、按条目错误隔离；让当前 6 组默认失败都有可定位原因。
2. **补全主要转换能力**：原版反向索引、纯纹理/局部覆盖、多目标与多方案分组；从最小闭合方案到真实样本验证。现有 RSZ 模板阻塞在这一阶段解决，不能留到界面完成后。
3. **加入隐藏语义与保留回退**：分离探测和必须迁移的检查；用小饰品反例约束误判，默认保留不确定模型。
4. **扩展声明穿戴规则**：保持独立分类注册，实现 rules.equip、来源追踪、手动覆盖、取消/读档恢复和关联包发布；复用现有组合与强制穿戴规则，验证新规则版本兼容。
5. **接入拖放 UI 和分发**：UI 只消费计划与事件；单 EXE 构建纳入压缩格式支持与依赖缺失体验，保持现有 `gui_self_test` 窗口启动检查，并加入队列/选择/完成页的关键交互验证。

本提案不预先更换 GUI 技术栈。先按当前 Python + Tkinter 核心验证拖放、后台任务和中文路径的可行性；界面原型只是视觉与交互参考。新增拖放/解包依赖须在实现阶段核实许可、分发方式与冻结 EXE 行为，不能在设计稿中当成已经具备。

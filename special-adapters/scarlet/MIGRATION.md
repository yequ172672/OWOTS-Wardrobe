# Scarlet migration coverage

## Source and scope

The source implementation is the Little1113 `scarlet_native_adapter.lua` from
`Scarlet-Model-1.1.0` (SHA-256
`B280101CDEC954F73EACE41527379500E6367504644F775B72291FC2A160A272`). The
derived Lua is generated by `tools/derive_lua.py`; no original script or
`Onimusha_V-S_Loader.dll` is loaded or executed.

The runtime identity is the wardrobe selection and its verified BODY/HEAD/HAIR
catalog rows. Native body IDs 7482 and 28284 are checked as observations only;
they are never used as synthetic wardrobe IDs.

## Actor evidence

`actor-contract.json` records the complete joint-name lists and every source
role. The offline comparison in
`_validation/scarlet-manual-migration-20260915/actor-table-comparison.json`
shows 371 Scarlet player PFB instances versus 261 stock instances, with the
first 261 equal and 110 appended Scarlet instances. The appended constraint
components are therefore actor-level data, not a consequence of selecting a
different clothing mesh.

The actor comparison does not by itself make the extension portable. The
current PFB reader still encounters a versioned `via.dynamics.Ragdoll` mismatch
(Scarlet v10 at `0x5DF0`, game v12 at `0x56B0`), and no adapter code creates the
110 appended Scarlet instances. The two typed setting names are recorded, but
their fields and the Ragdoll layout are not guessed. The Lua preflight reports
`actor_contract_missing` before any rig, weapon, cloth, or native stage write.

The static `scarlet_hat_static` and `scarlet_no_hat_static` wardrobe packages
provide the selected body/head/hair catalogs and mesh dependencies. They do not
provide a whole-player actor replacement. A host may later bind an exact
private actor instance, or use an existing actor that already satisfies the
contract, but it must not alter the global player prefab.

## Dynamic resource closure

`manifest/runtime-path-map.json` is the authoritative machine-readable map. It
contains all 120 source-to-target entries for each static variant and the file
inventory/digests used by the offline resource builder. Shared `uvar` paths are
explicitly marked as game-provided. The adapter routes every dynamic resource
through the selected ID and checks the holder's read-back path.

The actor correction JCNS assets remain part of the actor contract. If a future
private actor package externalizes them instead of embedding them in its PFB,
the package must add their exact target bytes and digests before enabling the
actor. An absent dependency is a startup error, never a successful fallback to
the source MOD path.

## Lifecycle and failure behavior

The gate tracks session, selection revision, supporter address, entity address,
and restore state. Any identity change first pauses callbacks and restores the
old owner. A failed restore retains the lease in quarantine and retries only
after the old owner still matches. A foreign writer is preserved and prevents
release. Reentrant bridge queries fail closed and cannot recursively run the
restore handlers. Reset callbacks only set a scalar `restart_required` marker;
they never call native cleanup. Render/UI-side gate denials likewise only stop
the callback and queue restoration. `scarlet_gate.flush_restore()` is called by
the known game-thread application callback, where the registered native restore
handlers for the private-parts router, Prop leases, sheath release, and dynamic
isolation may run. The read-only actor resolver flag is propagated through the
coherent-cloth and hip decorators, so a render-side preflight cannot retire a
native source lease. A failed flush remains pending and cannot re-enable the
adapter.

No save data, public equipment IDs, global catalogs, or external weapon MOD
objects are mutated. The static head/hair routes are authoritative once the
bridge reports exact catalog rows; the legacy dynamic parts router then remains
inactive.

## Acceptance boundary

The candidate has offline .NET lifecycle/math tests and static path/resource
evidence. It has not been installed into or run against the game process. The
first live run must capture the gate/adapter status and test actor replacement,
scene changes, both static variants, native fallback, and a foreign weapon
writer before any claim of dynamic equivalence is made.

版本：v0.3
日期：2026-09-14  
状态：独立服装、武器外观及 REF 菜单已完成阶段实机验证；存档关联、场景生命周期及原生菜单接入仍未完成。详细验证范围见运行时研究文档。

## 1. 目标

让多个服装和武器 MOD 作为额外条目同时安装，玩家可以在游戏中选择、切换或取消这些条目。每个 MOD 可以引用自己的资产，不必通过覆盖同一份原生服装、武器、骨骼或物理资源来实现外观替换。

核心交付是“额外的服装和武器外观、多 MOD 共存、游戏内切换”。独立属性、特殊逻辑等是后续扩展，不能成为初版外观 MOD 的必填项。

### 当前开发优先级（用户最新确认）

先完成核心功能与 UI，暂停武器伤害、防御判定等属性的专项调查和属性注册开发。属性功能为备选扩展，不阻塞当前外观版本交付；外观切换继续不得写入原生实际装备或属性。

当前先完善服装与武器独立选择、切换与取消、条目与错误提示、场景重建后的资源生命周期，以及与对应存档关联的选择恢复。REF 菜单已获用户实机确认，可继续作为当前版本操作入口；保留原生 UI 优先的方向，不据此宣称原生菜单无法扩展。

A4–A6 中伤害和防御数值的专项对照暂缓；武器外观切换、取消与实际装备身份保持仍属于核心范围。未做数值验证的内容不得标为已通过。

## 2. 术语与状态

### 2026-09-14 新增开发要求

- 独立服装菜单允许在存档点之外换装；必须与原生服装菜单同步当前状态。原生服装的选择走游戏实际服装逻辑，MOD 外观仍需保留独立身份，不能将某个原生服装伪标为该 MOD。再次打开原生菜单时应能识别当前 MOD，并避免过期原生选中状态无提示覆盖外观。原生菜单增加 MOD 行或状态展示的具体接入待实测。
- 主菜单改为独立窗口，不嵌在 REF 菜单中。建议默认使用键盘 `/ ?` 键所在物理按键触发，提供可修改绑定；中文或其他键盘布局下的实际键码需测试。提供列表/卡片模式、服装/武器分类、图标、名称、描述、当前选择和加载/错误状态。缺少图标与描述仍可正常使用。
- Mesh 插件导入流程与工作区导出增加服装系统支持。先设计方案供用户确认，未确认前不修改 Mesh 导入/导出代码。方案应覆盖独立路径、Prefab/Catalog、MMI/MDF/TEX 与物理依赖、配置和预览图、现有工程迁移，并继续禁止新增骨骼兼容性验证。
- 用户暂时无法人工验证，允许继续自主开发、静态验证和已授权实时诊断。到必须人工接手且无其他可推进工作时关闭游戏，记录接手步骤；不将缺少人工验收的功能报告为通过。

| 名称 | 含义 |
| --- | --- |
| 原生装备 | 玩家通过游戏原生装备逻辑实际穿戴的装备，例如普通武器、终极武器 |
| MOD 条目 | 系统中可独立识别和选择的一套服装或一件武器外观 |
| 外观选择 | 玩家在原生装备之外选中的 MOD 外观；可以取消并恢复原生外观 |
| 原生武器属性 | 当前实际装备的原生武器所提供的属性和效果，包括伤害、防御判定时间等 |
| MOD 属性 | 后续支持属性注册时，由 MOD 明确注册的武器属性；初版不要求提供 |
| 独立资产 | 使用 MOD 自己的资源标识或路径加载的网格、材质、纹理、骨骼、物理等资源 |

系统需区分“实际装备的原生武器”和“当前显示的 MOD 外观”。切换外观不得把原生武器身份丢失，也不得把外观继承到的属性误记为 MOD 自己注册的属性。

## 3. 初版必需范围

### R1. 多 MOD 注册与共存

- 安装服装 A、服装 B 后，两个条目都能被系统识别，玩家可在同一游戏会话内切换。
- 武器外观同样支持多个条目共存和选择。
- 条目应具有可独立识别的标识和显示名称，避免同名显示文本导致选择或保存混淆。
- 系统允许 MOD 使用各自的资产引用，不要求所有 MOD 将资源重命名为同一个原生资产路径。
- “注册”指加入系统的可选条目集合。能否同时注册到原生游戏目录和菜单，需要调查，不能在需求阶段视为已实现。

### R2. 游戏内切换与恢复

- 玩家可以选择服装 A、切换服装 B，并取消 MOD 服装以恢复相应原生外观。
- 玩家可以选择、切换或取消武器 MOD 外观。
- 服装外观选择和武器外观选择应分别保存，不因切换另一类外观而被无故清除。
- 初版以整套服装切换为基础；部位混搭不是初版验收条件。
- 游戏内切换是核心能力，不应要求玩家每次替换文件后重启游戏才能选择另一套已安装 MOD。具体允许切换的场景及必要的加载等待，应由调查结果确定。

### R3. 独立骨骼与物理资产

- 服装 A 可以引用自己的骨骼和物理资产，服装 B 可以引用另一组资产，两者同时存在。
- 切换条目时，系统负责应用该条目指定的资源引用，无须顶替原生骨骼或物理资源文件。
- **服装系统不验证骨骼是否符合游戏要求，不检查骨名、层级、绑定关系或动画兼容性。**
- **系统不修复骨骼、不转换骨骼，也不提供动画重定向。MOD 作者自行确保资产符合游戏自身限制。**
- 技术调查只需明确新增资源路径如何加载，以及切换时如何应用、绑定和释放对应资源。不得把骨骼验证器作为注册条件或初版前置任务。
- 此处的独立资产能力不意味着任意骨架都能被游戏正确播放；系统只承担资源引用和切换职责。

### R4. 外观与武器属性规则

#### R4.1 初版：没有 MOD 属性时保留原生武器属性

初版 MOD 可以只提供外观，不注册任何属性。应用此类 MOD 后，保留玩家实际装备的原生武器属性，不根据 MOD 的模型来源或名称替换属性。

| 操作顺序 | 最终外观 | 最终属性 |
| --- | --- | --- |
| 装备终极武器 → 选择未注册属性的 MOD A | MOD A | 终极武器属性，包括其更高伤害、更长防御判定等 |
| 装备普通武器 → 选择未注册属性的 MOD A | MOD A | 普通武器属性 |
| 装备终极武器 → 选择 MOD A → 切换到未注册属性的 MOD B | MOD B | 终极武器属性 |
| 装备普通武器 → 选择 MOD A → 取消 MOD 外观 | 普通武器原生外观 | 普通武器属性 |

同一个纯外观 MOD 可以在不同原生武器基础上使用，并分别保留相应原生武器的属性。不得把应用 MOD 的操作变成固定装备某一把原生武器，例如始终切换到普通武器或终极武器。

初版不要求 MOD 提供独立招式、攻击判定、动画或属性表；应保留原生装备的相关行为。具体模型与原生武器类别之间的适用范围仍需调查。

#### R4.2 后续扩展：MOD 已注册属性时优先采用 MOD 属性

当系统后续支持武器属性注册，且当前 MOD 已注册属性时，优先采用 MOD 属性；未注册属性的 MOD 继续遵守 R4.1。

属性来源优先级：

```text
系统已支持属性注册，且当前 MOD 已注册属性
    → 优先采用 MOD 属性
否则
    → 保留当前实际装备的原生武器属性
```

| 场景 | 预期属性来源 |
| --- | --- |
| 终极武器 + 无属性 MOD | 终极武器 |
| 普通武器 + 无属性 MOD | 普通武器 |
| 终极武器 + 已注册属性 MOD（后续支持） | MOD |
| 普通武器 + 已注册属性 MOD（后续支持） | MOD |
| 从有属性 MOD 切换为无属性 MOD（后续支持） | 当前原生武器，不继承上一个 MOD 的属性 |
| 取消有属性 MOD（后续支持） | 当前原生武器，不残留 MOD 属性 |

这里确认的是属性来源优先级。属性注册格式、可覆盖字段，以及“只注册部分属性”时的合并规则尚未定义，应在开发属性功能时另行确定。初版不应为此实现完整属性系统。

### R5. 界面优先级

1. 优先调查能否为原生服装、武器选择菜单增加额外 MOD 条目，并接入原生选择流程。
2. 原生菜单不能扩展时，允许使用 REFramework 自定义菜单，同时尽可能复用原生装备和资源加载逻辑。
3. 原生条目系统也不能动态扩展时，由 REF 维护独立条目集合和外观选择状态，负责调度资产切换。

原生 UI 是否可扩展、底层条目能否新增、独立资产能否加载，应分别判断。例如 UI 不能增加选项，并不自动意味着底层加载和装备逻辑也不可复用。

无论选择哪种路线，都应满足相同的多 MOD 共存、游戏内切换和武器属性优先级要求。

### R6. 保存与读档

- 优先让外观选择跟随对应游戏存档保存和恢复。
- 无法接入原生存档时，用 REFramework 独立记录选择，并关联对应游戏存档，避免不同存档之间串用外观选择。
- 保存信息应能区分服装选择、武器外观选择与原生装备身份；不得把一次继承的原生属性永久固化为 MOD 属性。
- 读档后按“原生实际装备 + 已保存的外观选择 + MOD 属性优先级”恢复状态。
- 保存关联键、存档槽/角色/周目之间的关系以及写入时机，由后续技术调查确定。

## 4. MOD 条目内容

下表规定能力范围，不是最终文件格式，也不要求所有资源都由每个 MOD 重新提供。

| 内容 | 要求 |
| --- | --- |
| 独立标识、类型、名称 | 支持区分服装和武器条目，用于选择和保存 |
| 网格与相关外观资源 | 能指定条目自己的资源；组织方式随实际游戏加载机制确定 |
| 材质、纹理 | 支持独立引用；允许在适用时复用已有资源 |
| 骨骼、物理 | 支持条目独立指定；不是每个 MOD 都必须新增，也不进行兼容性验证 |
| 图标 | 希望支持独立图标；缺省图标不阻碍初版外观注册与切换 |
| 附加逻辑 | 可选、后续扩展；不能作为纯外观条目的必填项 |
| 武器属性 | 可选、后续扩展；缺省时保留原生实际装备属性 |

## 5. 建议行为与待确认细节

以下是实施设计时需要收敛的细节，不改变已经确认的核心要求：

- **MOD 外观启用期间更换原生武器**：建议继续保留 MOD 外观，同时把底层实际装备和继承属性更新为新原生武器；是否需要因武器类别不适用而取消外观，应结合原生行为确定。
- **存档引用的 MOD 已被卸载**：建议回退到对应原生外观并保留正常原生装备，给出缺失条目提示；具体记录保留策略待定。
- **资源缺失或加载失败**：建议保留原先外观或恢复原生外观，避免半套资产残留。资源定位/加载错误处理不等于骨骼兼容性验证。
- **重复 MOD 标识**：需要可预测的冲突处理规则，不能无提示地随机选中其中一个。
- **资源生命周期**：需明确切换、读档和场景重建时哪些对象由系统持有和释放，避免引用已卸载资源。
- **切换场景限制**：加载、过场、死亡、战斗等状态下是否允许切换，依据实际引擎行为决定并在 UI 中反馈。

## 6. 初版验收场景

| 编号 | 操作 | 通过条件 |
| --- | --- | --- |
| A1 | 同时安装服装 A、B | 两个条目可独立选择，不争用同一原生替换文件 |
| A2 | 游戏中 A → B → 原生外观 | 外观正确切换并可恢复，已安装条目不要求靠反复换文件重启来选择 |
| A3 | A、B 各引用自己的骨骼与物理资源 | 切换时使用对应资源，原生资源文件不必被覆盖；不运行系统级骨骼兼容性验证 |
| A4 | 终极武器 → 无属性 MOD C | 显示 C，伤害、防御判定等继续来自终极武器 |
| A5 | 普通武器 → 同一个无属性 MOD C | 显示 C，属性继续来自普通武器 |
| A6 | 武器 MOD C → 无属性 MOD D → 取消外观 | 切换不改变原生实际装备属性，取消后恢复该装备原生外观 |
| A7 | 服装和武器外观同时启用 | 两类选择可共存，切换其中一类不无故清除另一类 |
| A8 | 保存并重新读入对应存档 | 恢复服装和武器外观选择，属性来源仍符合 R4；另一存档不串用选择 |
| A9 | 条目未提供图标、附加逻辑或独立武器属性 | 不因缺少这些可选内容阻止基本外观注册与切换 |

属性功能未来另行验收：有属性 MOD 优先使用自身属性；切换到无属性 MOD 或取消 MOD 后恢复当前原生装备属性，无上一 MOD 属性残留。

## 7. 技术调查清单

1. 原生服装与武器条目的定义位置、标识分配、注册/枚举时机和可扩展性。
2. 原生菜单是否允许新增条目、名称和图标；菜单显示与实际装备逻辑的耦合关系。
3. 资源加载器能否解析新增 MOD 路径，网格、骨骼、物理及材质之间如何引用。
4. 外观切换的应用入口、重建时机，以及骨骼和物理引用如何随条目切换。
5. 原生实际装备、属性来源与显示资产能否分离，如何保留终极武器等原生装备效果。
6. 原生存档扩展方式，或 REF 独立记录与游戏存档的可靠关联方法。

调查结论需要区分“已从源码/类型结构确认”“已在运行时验证”和“尚未确认”。现有 MCP 可辅助调查，但其通用查询和基础游戏接口已连通，并不证明本需求中的动态注册、独立骨骼引用或原生 UI 扩展已可行。

## 8. 初版不包含

- 骨骼兼容性验证、自动修复、自动转换、动画重定向。
- 强制所有 MOD 具备独立骨骼、物理、图标、脚本或属性。
- 完整的部位混搭、独立武器属性编辑、招式制作或技能系统。
- MOD 下载平台、商城或通用资源制作工具。

本需求文档确定行为与优先级，不指定未经验证的引擎 API、资源格式、注册文件格式或最终模块实现。

# OWOTS Wardrobe system repository

Standalone repository for the Onimusha WotS (OWOTS) wardrobe/appearance system and
the loose/PAK mod converter. Split out of the sibling `re-engine-mcp-CN` MCP
repository on 2026-09-16 so the MCP checkout stays upstream-focused.

## Subdirectories
| Directory | Purpose |
| --- | --- |
| `appearance-core` | Manifest registry, five-category composition (normal + transform), save/sidecar logic, preferences and the lab bundler (`build_lab.py`) |
| `reframework` | In-game wardrobe plugin source (`plugins/source/OWOTSAppearanceLab.cs`) and the inert 2B retirement marker (`autorun/`) |
| `mod-converter` | Standalone loose/PAK appearance converter and diagnostic reports |
| `release-tools` | Reproducible OWOTS test-release packaging, install, verify and rollback helpers plus the offline plugin compile check (`Verify-LabCompile.ps1`) |
| `release` | Local converter and wardrobe distribution packages and checksums; entirely ignored by Git |
| `special-adapters` | Dedicated scripted-MOD migrations (Scarlet, YoRHa 2B) kept separate from the converter |
| `docs` | Requirements, runtime/UI/save research, the independent-skeleton contract and the MOD authoring guide |

## Dependencies
- .NET 10 SDK/runtime (appearance core, plugin compile at game runtime); Python 3 for the converter and the lab bundler; CMake/Visual Studio only for the sibling native REFramework branch.
- Blender 5.2 is the adaptation and acceptance baseline for Mesh/asset work.
- Game data at `D:\gametest\steamapps\common\OnimushaWotS` stays read-only; never bundle game assets or saves in source releases.

## For AI Agents
- Converter appearance deduplication belongs to `mod-converter/appearance_duplicates.py`: compare effective content and resulting hide/equip choices, record covered native targets, and preserve uncertain or distinct appearances. Native target count is not outfit count. Keep distribution builds in ignored `release/`.
- Converter V2 keeps body/cloak/gauntlet separately registered. Schema 3 adds body `rules.equip` references; core selection applies them only for explicit body wear, retains later manual overrides, and reverses untouched defaults on cancel/change. Native apply rejects incomplete declared accessories even during restoration. Engine-forced companion parts must not duplicate any explicitly selected part from another category. Core regression and bundled runtime compilation pass; live acceptance of this new rule is pending. User scope excludes forced compatibility for special rigs/scripts.
- Independent skeleton is a single implementation in the plugin: `OWOTSAppearanceLab.MotionRebase` on `[Callback(typeof(LateUpdateBehavior), CallbackType.Post)]`. Keep the root `/90` stock and set `rootRest + (rest - rootRest)` on the changed root joints, where `rest` is the manifest `bindPositions` when declared, otherwise the equipped BODY mesh's `get_BaseLocalPosition`. The write must run on this late phase; `UpdateMotion`/`UpdateBehavior` writes were overwritten during normal gameplay. Never create a resource, hold a holder, or call the retired `DummySkeleton` swap.
- The enable switch is `WardrobePreferences.IndependentSkeleton` in the wardrobe settings; the runtime Lua controller was retired (no second writer, no second config).
- A mod's private `/90` fbxskel must never be installed at the game root skeleton path; keep it in the private mod directory (unused) or drop it.
- Deploy `build_lab.py` output, never the unbundled lab source. Per user instruction (2026-09-18), final distribution packages belong in this repository's Git-ignored `release/`. Private test assets, build intermediates and diagnostic evidence remain in workspace `_validation/`.
- Converter/skeleton evidence lives in workspace `_validation/` (e.g. `owots-joint-rebase-probe-20260916`, `wardrobe-hotreload-20260916`), outside this repo.
- Menu / main-menu character sharing is implemented in the same plugin (not a second writer): `PlayerManager.getControllingPlayerCharacterUI()` + `requestChangeModelPlayerUI(PARTS_TYPE,int)` push the selected MOD IDs, `PollUiCharacter` re-pushes after menu rebuilds, and both the joint rebase (`s_uiRebaseEntries`) and declared-part hiding (`PollVisibility`) cover the UI character. Enable switch is `WardrobePreferences.UiCharacterSync` (default true).
- Four-category apply merges outfit and weapon into one physical entry and switches MODs atomically: the new prefabs preload while the old MOD stays applied, then one game-thread call withdraws, registers and republishes the selection; the previous parts go to `s_retiringParts` and are released only after `_ModelIDs` moves off them. Runtime IDs are per-combination (`runtime.wardrobe.<kind>.<comboKey>`) because the native `checkModelChange` compares model IDs.
- Never let the synthetic `runtime.wardrobe.*` identity enter the legacy outfit/weapon projection or a sidecar record: `SanitizeLegacyId`/`LegacyState`/`SanitizeSelections` guard reads and writes, and `SyncActiveMods` republishes the real per-kind MOD ids after an apply.
- Native costume-menu work is currently read-only: `InstallCostumeHooks` captures `GUI030106` and observes `cCostumeList.onUpdateItem` (`GridIndex`, count, name) for `costume_menu_inspect`; no native row, text or thumbnail is written yet.
- `WardrobePreferences.AtomicSwitch` (default false) selects the switch strategy. Atomic mode swaps the selection in one native change but only rebuilds parts whose model ID changes, so engine-owned cloth parts must be pulled in as companions (`s_clothCompanionParts` = CLOAK/HAIR via `AddNativePart`) or the cloak keeps stale GpuCloth bindings and tears. Non-atomic restores first, which rebuilds everything but flashes the native model.
- Built-in (engine) appearances come from `app.user_data.CostumeItemTable._ItemList` (`gamedesign/gui/costumechange/costumeitemdata.user`). Entries are constructed lab-side as `WardrobeRuleEntry`/`WardrobeManifestEntry`, merged into the registry snapshot by `ReadWardrobeRegistry`, and carry parts as "empty Catalog + Prefab = native model ID"; `BeginOutfit` resolves them through `AddNativePart`. Applying is pure appearance (no native equipment or save writes). A missing engine prefab means an absent DLC asset and must refuse instead of building a broken model. NPC rows (`_NpcIndex >= 0`) are excluded; `PURCHASED_DLC` rows are marked as DLC. Real item names still need `ItemData.getDataFixedId(id).NameGuid` plus a message lookup that the type database does not currently expose.
- The window footer (`DrawFooter`) shows author/feedback/contact links (blue, clickable via `Process.Start UseShellExecute`) and the version. `CheckForUpdates` runs once on a background task and compares `CurrentVersion` with the latest GitHub release tag of `yequ172672/OWOTS-Wardrobe` (a 404/no release is treated as up to date). Keep `CurrentVersion` in sync with the published release tag. The entry list height derives from `GetContentRegionAvail().Y` so resizing shows more entries.
- Stock (upstream) REF compatibility: `ProbeCustomRefExtensions` treats the `owots_ui_icon_*` export as the marker for the custom build. Without it, icons fall back to placeholders and the wardrobe hotkey also taps REF's own menu key (`EnsureRefMenuOpen`, read from `re2_fw_config.txt` `REFrameworkConfig_MenuKey_V2`, default Insert) so both windows appear together and the cursor is released. Never hard-depend on a custom export outside a guarded probe.
- The wardrobe UI is localized through `T(zh, en)` plus `s_chineseUi`, which is set by the static constructor from `CultureInfo.CurrentUICulture`/`InstalledUICulture` (Chinese system -> Chinese, every other locale -> English). `s_chineseUi` must stay ahead of field initializers that call `T` (hence the static constructor). Built-in entry names come from the game's own localized message table, so they follow the game language; only our suffixes/descriptions are localized here. Localized text never crosses into native calls, catalogs or save fields.
- Built-in entries derive visibility from `PlayerModelVisualSettingParam.cBodySetting` (`IsInvisibleHead`, `IsVisibleCloak`) and pull the engine-forced `FixHairID`/`FixGauntletID` parts into the same change via `s_nativeExtraParts` (there is no "hide gauntlet" flag; the engine forces a specific gauntlet). Names come from `ItemData.getDataByFixedId(id).NameGuid` through `via.gui.message.get`. Icons are shipped in `reframework/builtin-icons/` and referenced per category index as `tex_<cat>_NN_imlm4.png`; DLC rows have no icon and fall back to the placeholder.
- Static candidates from 2026-09-16/17 (menu-character takeover, apply-poison fix, single physical entry, atomic-switch cloth companion fix, built-in entries with names/hides/forced parts/icons) are compiled and deployed; icon display and the doll gauntlet fix were user-confirmed, but other paths are NOT fully live-verified; see workspace `_validation/wardrobe-menu-char-20260916/HANDOFF.md` for scope, risks and the acceptance list.
- Fifth category (Oni/transform) S1 data layer is implemented (2026-09-18): `WardrobeCategory.Transform`, schema 4 manifests (`parts` for normal categories, `roots` = ONI_BODY/ONI_HEAD for transform), the R4 solver (`WardrobeComposition.ResolveTransform`: explicit selection wins, otherwise the game's own Oni look), expectation/snapshot separation (`WardrobeTransformSnapshotStore`) and schema 4 sidecars with legacy-version rebuild reporting plus a preserved `.legacy-vN.<hash>.bak` backup. No switch and no keep-normal policy (user decision v0.3). **Runtime transform handling is PAUSED (user decision 2026-09-20)**: the fifth category is marked unsupported in the UI (selection is saved only), all Oni runtime calls are disabled, and the implementation code is retained for the next iteration. P0 live findings: Oni resident objects exist in normal state and are reused; hiding them is sustainable (the lab implements it); `release`/`addPlayerResidentModel` are safe but do not rebuild live objects; the Oni hierarchy exposes the applied skeleton's joint names (OniBody 90/93) and a Transform-level rebase did not visibly change the shape (likely overridden by the `via.motion.Motion` 802-joint system); the live Oni mesh/material swap crashed the game (`_validation/transform-oni-20260918/crash-20260920-runtime-swap.dmp`) and is disabled. Transform entries may declare their own `skeleton` (bindPositions) and private root `mesh`/`material`. Older schema 2/3 manifests and v1-v3 sidecars are rejected with a re-convert/rebuild message, never migrated. Converter publishes schema 4 for normal categories; transform resource recognition is still pending (S2).
